# Security remediation — 10–11 October 2026

Release candidate based on main `0897a78f4d0599c4b5d3c0e0fc34056c94871bd7`. No live Supabase changes or credential rotations were performed. App deployment is held until the coordinated database prerequisites below are approved and verified.

## Fixed boundaries

Participant cookies are mandatory HMAC-signed, shape-checked, purpose-bound and expire after 30 days. They contain only participant ID, pool ID and session version; display names come from the matching database row, so long legacy names remain recoverable. Every authenticated read checks current membership and version. Recovery increments the version and invalidates all older participant cookies. No unsigned fallback exists. Admin cookies use signed eight-hour tokens; cookie API mutations require exact Origin. Explicit API credentials use the same durable budget as admin login. Cron routes fail closed when their secret is missing.

Private pool/passcode/participant/pick data lose anonymous/authenticated access. Public reference tables lose client writes. Server private reads are scoped to the authenticated pool. Service-only atomic pick saves lock/check pool, participant/version and series, reject completed/locked series and locked picks, and validate team and games. The unversioned RPC overload is removed. Odds select the newest snapshot deterministically.

Organizer-assisted recovery requires selecting the exact pool/member and explicitly confirming independently verified identity. Issue/reissue creates a cryptographically random 256-bit code valid for 30 minutes; only its SHA-256 digest is stored. The code appears once in a non-cacheable authenticated response, never a URL or log. Redemption atomically consumes it and increments the version; picks and names remain unchanged. A lost response can require the organizer to issue a replacement code. A display name or shared pool passcode alone is not identity proof.

A PostgreSQL-backed fixed-window throttle commits before checking credentials, works across serverless instances, fails closed, and trusts no forwarded IP headers. Four fixed rows cap growth. Per 15 minutes: join 30, admin login/API credential 5, recovery 10, authenticated issuance 10. Budgets are global: anonymous abuse can temporarily deny new login/join/recovery; existing valid admin cookies and participant sessions continue working. This conservative small-pool policy is an explicit availability tradeoff, not per-user throttling.

## Coordinated release procedure and blockers

1. Verify a restorable backup and review the actual schema/grants, then test both SQL files on a disposable copy. Apply `supabase/migrations/20261010_security.sql` followed by `20261011_account_recovery.sql` only with separate approval for live database access-policy changes. The second migration deliberately rolls back on case/space-normalized name collisions; the organizer must resolve identity explicitly, never automatically merge/delete/rename records.
2. Verify independent PostgreSQL transactions for concurrent redemption/reissue/pick writes and failed-attempt persistence. Local PGlite executes PostgreSQL but serializes requests in one instance; it does not prove multi-connection races or hosted Supabase behavior.
3. Verify existing SESSION_SECRET and ADMIN_SECRET each contain at least 32 random characters, and CRON_SECRET is nonempty. Values must not be printed. Key creation/rotation needs separate approval. App/database changes must be coordinated: older app versions rely on removed anonymous reads; the new app requires new RPCs/version fields. Roll forward with a compatible app if needed; do not restore permissive public policies as a rollback.
4. All old cookies become invalid. Have an organizer available to verify identities and issue recovery codes through the new admin page. Existing names remain reserved. Deploy the exact tested app only after database checks pass, then check unauthorized requests and organizer/member flows with approved test accounts.
